# 本地未归档草稿恢复设计

## 意图

用户持续要求直接优化。现有“新建会议”确认框避免了误点清空，但刷新、误关标签页或浏览器异常仍会丢失未归档的主题和逐字稿。本设计增加一个仅在当前浏览器保存的可恢复文本快照，并在下次打开时由用户明确决定是否恢复。

## 目标

- 使用独立的 `meeting-demo.draft.v1` 本地存储键保存最新的一份未归档草稿。
- 快照只包含 `meetingId`、`topic`、`transcript`、`savedAt`；绝不包含 API Key、Host、音频、WebSocket 状态、录音状态或千问生成结果。
- 输入、演示分段和最终实时转写会在短暂防抖后写入；`pagehide` 尽力同步落盘。
- 启动时发现有效快照，展示“恢复上次草稿 / 丢弃草稿”原生对话框；不静默覆盖空白工作区。
- 恢复只还原主题、逐字稿和会议 ID，录音保持停止，纪要标记为需要重新生成，绝不重新发送千问请求。
- 成功持久化归档或用户明确丢弃/新建会议时，仅清除属于当前会议 ID 的草稿快照。
- 快照损坏、过大或存储不可用时，应用和历史功能继续可用；最新文本超限时保留上一份有效快照并告知用户。

## 非目标

- 不做云同步、账号、服务端草稿、草稿列表、多设备恢复或多标签页当前草稿同步。
- 不恢复录音、麦克风权限、进行中的 Paraformer 会话或进行中的千问请求。
- 不恢复可能与已编辑逐字稿不匹配的千问纪要。
- 不改变现有历史 20 条上限、历史跨标签同步或 API Key 边界。

## 方案比较

1. `beforeunload` 警告：不能应对崩溃/刷新后的恢复，且用户仍会失去文本；不采用。
2. 单一、版本化本地草稿快照：实现小、无后端、明确恢复行为，覆盖高频丢稿路径；采用。
3. 多草稿/按标签页索引：可保留并行标签页内容，但引入冲突、清理和历史 UI，超出本轮需求；不采用。

## 设计

- 使用 300ms 防抖写入和 `pagehide` 刷新。快照只在当前会议有可恢复文本且尚需恢复时写入。
- 读取时严格验证字段类型、ISO 时间、会议 ID、主题长度与逐字稿长度；无效快照不阻止页面启动。
- 启动时仅当历史中已有相同 `meetingId`、主题和逐字稿的内容时，才将快照判定为已归档的陈旧副本并清除；同一会议归档后的新编辑必须仍可恢复。
- 草稿 `storage` 事件不会改写另一标签页正在显示的工作区；最后写入者仅影响下次启动时可恢复的快照。
- 恢复对话框要求“恢复”或“丢弃”的显式选择；Escape 会保留对话框与待恢复快照，不进入一个不能继续保存的半关闭状态。
- 存储失败只显示本地告警或维持当前页面，绝不清空用户输入；历史归档失败时仍视为需要确认才能丢弃的未持久化内容。

## 验收

- 编辑主题和逐字稿后刷新，选择恢复可还原文本，不会触发千问请求或伪造纪要。
- 选择丢弃后，再次刷新不再显示恢复框。
- 成功归档或确认新建后，对应快照被清除。
- 损坏快照不会阻止启动或清空当前历史。
- 其他标签页的草稿存储事件不改写当前草稿。

## 已知限制

- 只保留最新的一份草稿；并行标签页可能互相替换可恢复快照，但不会通过事件实时覆盖可见工作区。
- 对于发生在最后一次防抖写入和 `pagehide` 之前的灾难性浏览器终止，最新少量输入仍可能无法恢复。
