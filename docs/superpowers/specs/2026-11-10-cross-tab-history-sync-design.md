# 同源多标签本地历史同步设计

## 意图

会议历史只保存在浏览器 `localStorage`，但页面目前只在启动时读取它。两个同源标签页先后生成纪要时，后一个标签页会把自己陈旧的内存数组整体写回，可能抹掉前一页刚保存的会议。此优化保护本地历史的完整性，不改变隐私边界。

## 已考虑的方式

- **保存前重读合并 + `storage` 事件同步（采用）：** 每次归档前读取当前持久化快照，合并本页尚未落盘的记录，再以现有去重、排序和 20 条上限写回；其他标签变更用 `storage` 事件刷新本页展示。它无需后端或权限。
- **Web Locks 串行化所有写入：** 可以处理真正同时的读取-写入竞争，但会显著增加浏览器兼容性和实现复杂度；本轮不承诺这种极端并发。
- **云端账户同步：** 与“仅保存在当前浏览器”的产品承诺冲突，不采用。

## 目标

- 同一浏览器、同一来源的标签页先后归档不同会议后，刷新仍能看到两条记录。
- 本页在收到其他标签的 `storage` 变更后更新历史列表、计数与详情，不改变当前会议主题、逐字稿、纪要或搜索词。
- 浏览器存储暂不可用、数据损坏或写入失败时，保留已有内存回退行为；不会为了同步清空当前页面的内存历史。
- 继续使用 `meeting-demo.history.v1`、现有去重规则、时间排序及 20 条上限。

## 边界

- 仅覆盖同源标签页**先后**写入；不承诺两个标签页在同一时刻读取旧值后同时写入时的原子性。
- 不新增 API、服务端、账号、云同步、历史编辑/删除功能或 API Key 存储。
- 外部清空本地历史时应被尊重；只合并本页明确尚未持久化的记录，避免复活已在另一标签页删除或淘汰的记录。

## 验收

- 模拟外部标签页在本页启动后写入一条历史，本页再生成纪要，持久化数据包含两条记录且当前草稿不变。
- 模拟 `storage` 事件后，已打开的历史筛选结果和计数反映外部记录，搜索词与当前草稿不变。
- 现有存储失败回退和完整测试套件持续通过。
