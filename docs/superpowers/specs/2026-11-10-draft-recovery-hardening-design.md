# 本地草稿恢复收尾加固设计

## 意图

上一轮本地草稿恢复已经保护了刷新、误关和归档失败后的主题与逐字稿。本轮收紧两个剩余边界：浏览器无法删除恢复快照时，界面不能谎称草稿已丢弃；草稿时间必须是页面自身写入的、可逆的 UTC ISO 时间，不能把任意可解析字符串当作有效恢复数据。

## 目标

- `clearPersistedDraft(meetingId)` 明确区分 `removed`、`missing`、`foreign` 与 `failed`。
- 恢复对话框只有在实际删除成功后才报告“已丢弃”；删除失败时保持对话框打开，在对话框内给出可被辅助技术读取的提示，并允许重试或恢复。
- 草稿在用户打开恢复框后被其他标签页删除或替换时，不删除替代快照，也不把该情况说成成功丢弃。
- 用户从“放弃当前会议”确认进入新建流程时，如果当前可恢复草稿删除失败，保留当前会议和文本，并说明未能新建，避免下次启动意外重新出现旧草稿。
- `savedAt` 仅接受 `Date.parse` 后能精确往返为 `new Date(timestamp).toISOString()` 的值。页面现有写入的时间继续有效；`"1"`、非 UTC 偏移、缺少毫秒或日历归一化日期（例如 2 月 30 日）无效。

## 非目标

- 不改变草稿仅保存 `meetingId`、`topic`、`transcript`、`savedAt` 的隐私边界。
- 不增加草稿列表、跨标签实时同步、云端同步、API Key 持久化或录音恢复。
- 不改变历史会议的保留、同步和导出行为。

## 方案比较

1. 继续返回布尔值并只修改成功文案：无法区分“没有对应草稿”“其他标签页替换了它”和“存储报错”，仍会误导用户；不采用。
2. 返回有限结果并按结果处理：保留最小接口，在删除失败时保留可操作的恢复界面，在竞争情形中不误删数据；采用。
3. 用正则限制四位年份时间：可以拒绝常见异常值，但会人为排除 `Date#toISOString()` 的扩展年份表示；不采用。
4. 解析后精确 ISO 往返校验：与页面写入方式一致，同时拒绝非规范或会被 JavaScript 归一化的日期；采用。

## 设计

- `clearPersistedDraft` 先读取和验证当前存储的快照。读取/解析/删除异常都返回 `failed`，不会尝试清除未知内容；缺失返回 `missing`；会议 ID 不同返回 `foreign`；只在 ID 相同且 `removeItem` 完成时返回 `removed`。
- 恢复框中增加独立的状态区域。`failed` 保留 `pendingDraftRestore` 与对话框，以便用户重试“丢弃草稿”或选择“恢复上次草稿”。`missing` 与 `foreign` 会关闭旧提示，但用不同的页面反馈说明真实结果；替代快照不被修改。
- “丢弃并新建”调用同一清理接口。仅当当前会议本来需要恢复且清理结果为 `failed` 时，取消重置并保持用户文本；空白或已归档会议不因不可读的孤立存储而被阻止新建。
- 时间验证使用 `Number.isFinite(Date.parse(savedAt))` 与 ISO 字符串精确比较，不依赖浏览器对宽松日期字符串的容错。

## 验收

- 模拟 `removeItem` 抛错后，恢复框仍打开、存储字节未变、框内出现警告；恢复正常后重试可删除。
- 已被删除或被不同会议 ID 替换的恢复快照不会被误删，也不会显示“已丢弃”。
- 确认“丢弃并新建”时删除当前恢复副本失败，主题与逐字稿仍留在页面中。
- 规范 `2026-11-10T09:30:00.000Z` 能触发恢复；`"1"` 与 `2026-02-30T09:30:00.000Z` 不会触发恢复。
